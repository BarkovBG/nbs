# Бекап снапшота: локи и порядок зависимостей

Бекапы в проде ещё не включались. Первый PR добавляет защиту источников и
ручную постановку одного снапшота вместе с его зависимостями. Массовый обход
folder и автоматическая постановка новых снапшотов относятся к следующей
версии. Документ публикуется отдельным PR.

## Постановка и результат

`snapshots backup --id C` транзакционно добавляет готовый C в CP-очередь и
отвечает `OK`, не ожидая копирования. Повторная команда сохраняет уже поставленную
попытку; для снапшота с `backup_completed=true` отвечает `OK` без новой работы.
Отсутствующий, создающийся или уже удаляющийся источник без завершённой копии
не принимается. Создание нового снапшота само по себе бекап не включает.

`snapshots get --id C` показывает `backup_completed`: успешное окончание
DP-копии записано в CP. `false` само по себе не различает ожидающую, не
запрошенную или отменённую попытку. `OK` команды означает успешную постановку
либо уже завершённую копию. Очистка очереди отметку успеха не выставляет.

У записи очереди есть `backup_id`: новый запрос после отмены получает новый
ключ отправки задачи, а задача удаляет именно свою запись очереди.

## Один граф за раз

Регулярная задача `ScheduleBackupSnapshotTasks` выполняется в одном экземпляре.
Она берёт записи очереди, отправляет `snapshots.BackupSnapshot` по ключу
записи и ждёт окончания каждой задачи, прежде чем перейти к следующей.
Запись очереди удаляет сама задача бекапа по окончании, поэтому следующий
запуск планировщика продолжает со следующей записи. Отдельной таблицы слота
и CP-удержаний нет: два графа с пересекающимися зависимостями просто не
исполняются одновременно, и повторного копирования общих источников не бывает.

## DP-ссылки задач лока

`backup_snapshot_refs` содержит только ключ `(snapshot_id, task_id)`.
Ссылку добавляет только `dataplane.LockSnapshotForBackup`: по одной задаче на
каждый снапшот графа, с ID самой задачи. Задача держит ссылку, пока её не
отменят; `Cancel` удаляет ссылку. Повторный захват и повторное освобождение
идемпотентны. Задача копирования собственной ссылки не берёт: пока копия
идёт, снапшот держит задача лока, которую CP отменяет только после копии.

DP-удаление начинается только при отсутствии всех ссылок. Оно проверяет их
диапазон и меняет статус снапшота в одной Serializable RW-транзакции; захват
читает готовность снапшота и добавляет ссылку в такой же транзакции. Если
удаление выиграло, ссылку не принимаем; если выиграл захват, удаление ждёт.
Прямой `DeleteSnapshotData` проходит эту же проверку до удаления карты и
ссылок на чанки.

## Подготовка графа

Для C, использующего чанки B и A:

1. Узел C есть в состоянии задачи. Перед запуском его лока сохраняем `Locked=true`.
2. `LockSnapshotForBackup` транзакционно удерживает C, читает создателей ненулевых chunk ID и сохраняет их список в metadata. Дальше задача ждёт отмены.
3. CP читает metadata через `GetTaskMetadata`. `Ready=true, Locked=true` добавляют создателей в граф новыми узлами. Для каждого готового и ещё не скопированного снапшота запускаем такую же задачу лока. `Ready=true, Locked=false` значит, что удаление выиграло захват: узел исключаем.
4. Когда все узлы обнаружены, копируем их по одному: создатели раньше снапшотов, которые используют их чанки. Порядок даёт обход в глубину по сохранённым связям. Циклов нет: создатель чанка существует раньше снапшота, который на него ссылается.

ID задачи лока не храним: повторный `ScheduleTask` с тем же ключом
идемпотентности возвращает ту же задачу. В узле остаются только связи и
признаки обнаружения, исключения, завершения и наличия лока.

Связи определяются по полной карте, а не только по `BaseSnapshotID`. Folder
зависимости не ограничивает. Уже завершённая копия становится завершённым
узлом без нового лока и копирования. Пока открываем родителей, удержанный
потомок сохраняет собственные ссылки на нужные ему чанки, поэтому граф не
нужно захватывать одной транзакцией.

## Удаление

Delete записывает статус `deleting` в CP сразу; физическое удаление ждёт
снятия DP-ссылки. Каждый снапшот держит собственные ссылки на все чанки,
которые использует, поэтому удаляемый узел можно пропустить в любой момент
до принятия его копии: нужные потомкам чанки скопирует сам потомок.

Когда до узла доходит очередь, перечитываем его статус. Удаляемый узел
исключаем и снимаем его лок; готовый принимаем, сохраняя точный DP-запрос.
Принятую копию заканчиваем, даже если снапшот начал удаляться.

| Ситуация | Действие |
| --- | --- |
| Delete до лока | Узел не удерживаем и не копируем |
| Delete после лока, до копии | Пропускаем узел, когда до него доходит очередь, и снимаем лок |
| Delete во время принятой копии | Заканчиваем копию, затем снимаем лок |

Удаляемый узел держится до своей очереди. Статус `deleting` виден сразу,
задерживается только физическое удаление, и только до конца копий его
предков.

После бекапа A можно удалить его исходные данные: C имеет собственные ссылки
на нужные чанки. Обычное DP-удаление снимает ссылки конкретного снапшота;
физически общий чанк удаляется после исчезновения последней ссылки.

## Копирование и освобождение

CP сохраняет точные метаданные, зашифрованный DEK и DP-запрос до отправки
`BackupSnapshotData`. Принятая копия повторяется до успеха или явной отмены.

DP ставит в очередь собственные чанки и чанки создателей без подтверждённой
копии. Чанки уже завершённых узлов использует повторно. Каждая позиция
полной карты сохраняется, даже если исходный создатель уже удалён. Чанк, который
воркер не смог скопировать, остаётся в очереди и достаётся следующему воркеру.

После всех чанков DP публикует полную карту и метаданные, сохраняет `Finished`
и удаляет записи чанков этого снапшота. CP сохраняет завершение узла вместе
с очисткой DP-запроса, выставляет `backup_completed`, отменяет задачу лока и
ждёт её окончания. Затем переходит к следующему узлу. Распаковка для CRC,
сравнение содержимого назначения и ремонт объектов в этот PR не входят.

## Сбой и отмена

Состояние CP — три поля: узлы, точный DP-запрос текущей копии и ID её задачи.
Граф готов, когда все узлы обнаружены. Следующий узел — первый в порядке,
который ещё не завершён или не исключён; узел закончен, когда снят его лок.
После рестарта повторяются только незаконченные шаги: завершённый узел с
неснятым локом снова записывает `backup_completed` и снимает лок.

Явная отмена сначала восстанавливает ID копии, отменяет её и ждёт окончания.
Метод `Cancel` DP-копии удаляет записи очереди и чанков этого снапшота;
следующая попытка ставит их заново. Воркер, уже читающий чанк, допишет объект
без карты либо запишет «completed» для чанка, который действительно лежит в
фолловере. После этого CP отменяет задачи лока всех узлов с `Locked=true`,
ждёт их окончания и удаляет свою запись очереди. Ошибка очистки повторяется;
она не считается успешной отменой.

## Шифрование

Сохраняется схема main: DEK шифрует данные; KEK на хосте сервиса шифрует DEK.
CP сохраняет зашифрованный DEK и передаёт DP. Каждый объект содержит свой
зашифрованный DEK и идентификатор KEK; AES-GCM получает случайный nonce при записи.

Чанк x, скопированный вместе с A, используется C с собственным конвертом x.
Удаление исходного A или его метаданных не лишает C ключа x: зашифрованный DEK
находится на самом объекте. Карта и метаданные C получают конверт попытки C.
Поддерживается одно настроенное поколение KEK; ротация требует отдельной работы.

## Отдельный PR: наполнение очереди по folder

Второй PR добавляет только автоматическую постановку в ту же очередь.
`snapshots backup-folder --folder-id <id>` сохраняет выбор каталога и отвечает
`OK`. В таблице `backup_folders` находятся `folder_id`, поколение включения и
`enabled`; владельцев графов или копий там нет.

`snapshots.BackupFolder` читает готовые источники без отметки завершения по
индексу каталога и курсору ID. Для каждого вызывает транзакционную постановку
в общую очередь. Состояние производителя — курсор и номер прохода; собственных
удержаний и задач копирования у него нет. Защиту и порядок зависимостей
обеспечивает тот же путь одного snapshot_id из первого PR.

После конца прохода курсор сбрасывается. Поэтому источник, ставший готовым
позади курсора, будет найден в следующем проходе. Новый номер прохода позволяет
повторно поставить ранее отменённую попытку с новым ключом. Повтор после сбоя
внутри прохода сохраняет ключ и не дублирует уже стоящую запись.

Новые снапшоты выбранного каталога ставятся в очередь той же транзакцией,
которая переводит их в `ready`. Появление C раньше A в обходе безопасно:
исполнение записи C раскроет граф и скопирует доступный A первым.

`--disable` прекращает автоматическую постановку. Уже поставленные запросы
продолжают исполняться; ручная постановка одного ID остаётся доступной.
Проверка поколения и вставка в очередь выполняются одной транзакцией, поэтому
старый производитель не может ставить записи после отключения или в новом
поколении включения. Пока запись только стоит в очереди и граф не удержан,
обычное удаление источника разрешено.

## Первое включение и границы

Сначала применяем CP/DP-схему (`backup_snapshot_refs` в DP, `backup_id` очереди
и `backup_completed` в CP) и обновляем все исполнители, затем разрешаем ручные
запросы. Старых исполнителей удаления, не проверяющих ссылки, к этому моменту
быть не должно. Включение конфигурации само не наполняет очередь. Для ручного
пути предварительный обход folder не нужен. Второй PR включает автоматическую
постановку отдельно командой выбора folder.

GC фолловера, удержания завершённых копий и аудит объектов остаются отдельно.
Пока GC не включён, завершённые зависимости доступны для следующей копии.
Перед GC нужны ссылки фолловера: удаление копии A не должно убрать чанки,
необходимые C, между завершением A и публикацией C. Отмена может оставить
объекты без опубликованной карты; их очистка требует отдельного протокола.
Живое старое исполнение задачи после потери lease на другом хосте не
ограждается: это ограничение фреймворка задач, а не протокола бекапа.

Добавлены сценарии DP-захвата против Delete, порядка A → C, пропуска
завершённого предка, отсутствующего предка, удаления листьев, восстановления
после сохранённого состояния, отмены и повторной постановки после очистки.
Проверены форматирование, импорты, регистрация файлов и дифф. Сборка и
исполнение тестов — только на cloud после публикации коммитов.
