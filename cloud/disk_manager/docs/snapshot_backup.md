# Бекап снапшота: удержания и порядок зависимостей

Бекапы в проде ещё не включались. Первый PR добавляет защиту источников и
ручную постановку одного снапшота вместе с его зависимостями. Массовый обход
folder и автоматическая постановка новых снапшотов относятся к следующей
версии. Документ публикуется отдельным PR.

## Постановка и результат

`snapshots backup --id C` транзакционно добавляет готовый C в CP-очередь и
отвечает `OK`, не ожидая копирования. Повторная команда сохраняет уже поставленную
попытку; для снапшота с `backup_completed=true` отвечает `OK` без новой работы.
Отсутствующий, создающийся или уже удаляющийся источник без завершённой копии
не принимается. Создание нового снапшота само по себе бекап не включает.

`snapshots get --id C` показывает:

| Поле | Значение |
| --- | --- |
| `backup_plan_id` | ID CP-задачи, удерживающей источник в графе |
| `backup_task_id` | ID CP-задачи, уже принявшей копирование этого источника |
| `backup_completed` | Успешное окончание DP-копии записано в CP |

`backup_completed=false` само по себе не различает ожидающую, не запрошенную
или отменённую попытку. `OK` команды означает успешную постановку либо уже
завершённую копию. Очистка очереди отметку успеха не выставляет.

У записи очереди есть `backup_id`: новый запрос после отмены получает новый
ключ отправки задачи. ID задачи используется для удержаний; `backup_id`
используется для идемпотентной отправки и удаления именно своей записи очереди.

## Один исполнитель очереди

CP-таблица `backup_plan` хранит владельца общего слота исполнения. Перед
захватом любого источника `snapshots.BackupSnapshot` занимает этот слот.
Повтор той же задачи продолжает свой план; другая задача ждёт, не удерживая
часть своего графа. Это предотвращает взаимное ожидание двух запросов с
пересекающимися зависимостями. Последовательность общая, без выбора folder.

Слот освобождается после завершения или явной отмены задачи и освобождения
всех её удержаний. Проверка по индексу `backup_plan_id` не позволяет начать
следующий граф, пока остался источник предыдущего. При ошибке копирования
текущая попытка продолжает восстановление; следующая ждёт её успеха или отмены.

## Подготовка графа

Для C, использующего чанки B и A:

1. Сохраняем намерение удержать C в состоянии задачи, затем захватываем CP-удержание на его строке.
2. DP-задача `GetSnapshotBackupDependencies` временно удерживает карту C, читает создателей ненулевых chunk ID, сохраняет ответ и освобождает своё удержание.
3. Добавляем найденные зависимости в сохранённый граф. Для каждого доступного, ещё не скопированного источника повторяем захват и чтение карты.
4. Сохраняем полный граф и топологический порядок. До этого шага копирование не запускаем.
5. Копируем A, затем B, затем C; после каждой полной копии и окончания её записей освобождаем источник.

Связи определяются по полной карте, а не только по `BaseSnapshotID`. Folder
зависимости не ограничивает. Уже завершённая копия становится завершённым
узлом графа без нового чтения и копирования.

Захват каждого CP-удержания и Delete сериализуются на одной строке снапшота.
Пока открываем родителей, защищённый потомок сохраняет собственные ссылки на
все необходимые унаследованные чанки. CP-удержание не позволяет задаче удаления
отправить DP-удаление этого источника. Поэтому граф не требуется захватывать
одной транзакцией.

Если A отсутствует или Delete выиграл до его захвата, A отмечаем исключённым.
Его полный снапшот не восстанавливаем. Нужный C чанк x сохраняется ссылкой C и
копируется через C. Если A удалось удержать, копируем его раньше C.

## Удаление

CP различает подготовку графа (`backup_plan_id`) и принятую копию
(`backup_task_id`). Delete может записать статус `deleting`, но физическое
удаление ждёт освобождения удержаний.

Перед каждым шагом копирования перечитываем незавершённые узлы. Готовые
источники и уже принятые копии являются корнями оставшейся работы. По связям
определяем, какие предки им нужны. Удаляющиеся узлы вне этого множества
исключаем, сохраняем решение и освобождаем.

| Ситуация | Действие |
| --- | --- |
| Delete до первого захвата источника | Новый источник не принимаем; нужные потомку чанки копируем из потомка |
| Удержанный A удаляется, живой C зависит от A | Держим A и копируем раньше C |
| Удаляется ненужный конец C, копия C ещё не принята | Освобождаем C; живые предки остаются кандидатами на бекап |
| Весь оставшийся граф удаляется, копии не приняты | Освобождаем граф без копирования |
| Delete во время принятой копии | Заканчиваем копию, затем разрешаем удаление |

Приём копии повторно проверяет статус транзакционно. Delete между обходом
графа и приёмом не позволяет принять удаляющийся лист. Удержанного удаляющегося
предка можно принять, если он нужен оставшемуся потомку. Гонка с удалением
потомка может вызвать лишнюю принятую копию предка; принятую работу заканчиваем.

После бекапа A можно удалить его исходные данные: C имеет собственные ссылки
на нужные чанки. Обычное DP-удаление снимает ссылки конкретного снапшота;
физически общий чанк удаляется после исчезновения последней ссылки.

## Копирование и освобождение

CP сохраняет точные метаданные, зашифрованный DEK и DP-запрос до отправки
`BackupSnapshotData`. Принятая копия повторяется до успеха или явной отмены.
DP транзакционно устанавливает удержание против `DeletingSnapshot`;
`DeleteSnapshotData` также проверяет его. Карта и зарегистрированные ссылки
остаются доступными до окончания работы.

DP ставит в очередь собственные чанки и чанки создателей без подтверждённой
копии. Чанки уже завершённых зависимостей использует повторно. Каждая позиция
полной карты сохраняется, даже если исходный создатель уже удалён.

Воркер сначала перечитывает выбранные ключи очереди и регистрирует чтение в
`backup_chunk_inflight` одной RW-транзакцией. Поэтому старый список, полученный
до отмены, не позволяет начать новую работу после очистки очереди. Регистрация
удерживается до завершения локальных операций записи и обновления результата.

После завершения чанков DP публикует полную карту и метаданные, сохраняет
`Finished`, дожидается учтённых воркеров и освобождает своё удержание. CP после
успешного окончания ребёнка сохраняет завершение узла и транзакционно выставляет
`backup_completed`, освобождая CP-удержания. Следующий узел стартует после этого.
Дополнительная распаковка для CRC, сравнение содержимого назначения и ремонт
объектов в этот PR не входят.

## Сбой и отмена

Состояние CP-задачи содержит узлы, зависимости, индекс открытия графа,
намерение отправить читателя, топологический порядок и индекс копирования.
Для текущей копии сохраняются точный DP-запрос и ID ребёнка. Каждый возможный
захват имеет сохранённое намерение; завершение сохраняется до освобождения.

Если отправка удалась, а child ID не сохранился, повтор отправляет тот же запрос
с тем же ключом и восстанавливает ту же задачу. После сохранённого `Finished`
DP повторяет только очистку и не записывает данные заново.

Явная отмена восстанавливает неизвестные ID читателя/копии, отменяет детей и
ждёт окончания. `ReleaseSnapshotBackup` в DP очищает очередь, ждёт учтённых
воркеров и снимает удержание. Затем CP освобождает источники графа и общий слот.
Ошибка очистки повторяется; она не считается успешной отменой. Проверка ID
задачи не позволяет старой отмене освободить удержание новой попытки.

## Шифрование

Сохраняется схема main: DEK шифрует данные; KEK на хосте сервиса шифрует DEK.
CP сохраняет зашифрованный DEK и передаёт DP. Каждый объект содержит свой
зашифрованный DEK и идентификатор KEK; AES-GCM получает случайный nonce при записи.

Чанк x, скопированный вместе с A, используется C с собственным конвертом x.
Удаление исходного A или его метаданных не лишает C ключа x: зашифрованный DEK
находится на самом объекте. Карта и метаданные C получают конверт попытки C.
Поддерживается одно настроенное поколение KEK; ротация требует отдельной работы.

## Первое включение и границы

Сначала применяем CP/DP-схему и обновляем все исполнители, затем разрешаем
ручные запросы. Старых исполнителей удаления, не проверяющих удержания, к этому
моменту быть не должно. Включение конфигурации само не наполняет очередь.
Предварительный обход folder в этой версии не нужен.

GC фолловера, удержания завершённых копий и аудит объектов остаются отдельно.
Пока GC не включён, завершённые зависимости доступны для следующей копии.
Перед GC нужны ссылки фолловера: удаление копии A не должно убрать чанки,
необходимые C, между завершением A и публикацией C. Отмена может оставить
объекты без опубликованной карты; их очистка требует отдельного протокола.

Учёт воркеров по логическому task ID предполагает прекращение предыдущего
исполнения задачи. Он не ограждает живое старое исполнение после потери lease
на другом хосте и сам по себе недостаточен для будущего GC.

Добавлены сценарии CP/DP-захвата против Delete, порядка A → C, пропуска
завершённого предка, отсутствующего предка, удаления листьев, восстановления
после сохранённого состояния, отмены и ожидания воркеров. Проверены форматирование,
импорты, регистрация файлов и дифф. Сборка и исполнение тестов — только на cloud
после публикации коммитов.
