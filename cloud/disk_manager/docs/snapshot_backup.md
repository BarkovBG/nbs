# Бекап снапшота: лок копии и учёт чанков в фолловере

Бекапы в проде ещё не включались. Первый PR добавляет защиту источников и
ручную постановку одного снапшота. Массовый обход
folder и автоматическая постановка новых снапшотов относятся к следующей
версии. Документ публикуется отдельным PR.

## Постановка и результат

`snapshots backup --id C` транзакционно добавляет готовый C в CP-очередь и
отвечает `OK`, не ожидая копирования. Повторная команда сохраняет уже поставленную
попытку; для снапшота с `backup_completed=true` отвечает `OK` без новой работы.
Отсутствующий, создающийся или уже удаляющийся источник без завершённой копии
не принимается. Создание нового снапшота само по себе бекап не включает.

`snapshots get --id C` показывает `backup_completed`: успешное окончание
DP-копии записано в CP. `false` само по себе не различает ожидающую, не
запрошенную или отменённую попытку. `OK` команды означает успешную постановку
либо уже завершённую копию. Очистка очереди отметку успеха не выставляет.

У записи очереди есть `backup_id`: новый запрос после отмены получает новый
ключ отправки задачи, а задача удаляет именно свою запись очереди.

## Очередь

Регулярная задача `ScheduleBackupSnapshotTasks` берёт записи очереди и
отправляет `snapshots.BackupSnapshot` по ключу записи. Каждая задача
бекапит один снапшот; запись очереди удаляет она же по окончании. Задачи
разных снапшотов идут параллельно: у каждого снапшота свои записи чанков, а
общие чанки учитываются в фолловере.

## Лок на копируемый снапшот

Пока снапшот существует, записи его карты держат счётчики ссылок на все
чанки, которые он использует, в том числе созданные другими снапшотами. Если
A удалят, чанки A, нужные C, останутся. Поэтому копии C достаточно удерживать
только сам C: его карту и его записи о чанках. Предков и порядок копий
учитывать не нужно.

Копию держит колонка `backup_task_id` в DP-строке снапшота, рядом с
`lock_task_id` инкрементных снапшотов. Отдельная колонка нужна, чтобы бекап
базы не задерживал создание инкремента от неё и наоборот. У снапшота
одновременно не больше одной копии: одна запись очереди, а новая попытка
начинается только после очистки отменённой.

`dataplane.BackupSnapshotData` в начале транзакционно читает строку и, если
снапшот готов, записывает в колонку свой task ID; повтор тем же ID
идемпотентен. В конце или при отмене очищает колонку, если в ней его ID.
Если удаление уже выиграло, колонку не трогаем, и задача просто
заканчивается. CP после копии ставит `backup_completed` только готовому
снапшоту: DP-удаление начинается лишь после того, как CP пометил снапшот
`deleting`, поэтому пустая копия удаляемого снапшота отметку не получит.

DP-удаление в той же транзакции, где меняет статус на `deleting`, проверяет
колонку и ждёт, пока она не опустеет. Захват и удаление меняют одну строку
в Serializable-транзакциях, поэтому выигрывает ровно одна сторона. Прямой
`DeleteSnapshotData` проходит эту же проверку.

## Учёт чанков в фолловере

Объект чанка лежит в фолловере по ключу ID чанка, поэтому один чанк нужен
там один раз, сколько бы снапшотов его ни использовали. DP-таблица
`follower_chunks` хранит ID чанков, чьи объекты уже записаны. Воркер добавляет
чанк туда в той же транзакции, где отмечает его копию. Постановка в очередь
пропускает чанки из этой таблицы.

Копия снапшота переносит все чанки своей карты, которых ещё нет в фолловере:

- Бекап включён заранее: чанки предков уже записаны их копиями, и новый снапшот переносит только свои. Объём тот же, что при копировании «только своих» чанков, но без условия, что копия предка закончена.
- Первичный backfill цепочки, где старые снапшоты удалены: общий чанк удалённого создателя переносит первый снапшот, который его использует, остальные пропускают.

Отдельное копирование «только своих» чанков опасно: если копия создателя не
закончена или создатель удалён, в фолловере окажется карта со ссылками на
отсутствующие объекты.

## Удаление

Delete записывает статус `deleting` в CP сразу; физическое удаление ждёт
только ссылки идущей копии.

| Ситуация | Действие |
| --- | --- |
| Снапшот удаляется до начала бекапа | Копию не запускаем |
| Delete выиграл захват копии | Копия заканчивается без копирования, отметки нет |
| Delete во время копии | Заканчиваем копию, затем удаление продолжается; отметки нет |

После бекапа A можно удалить его исходные данные: C имеет собственные ссылки
на нужные чанки. Обычное DP-удаление снимает ссылки конкретного снапшота;
физически общий чанк удаляется после исчезновения последней ссылки.

## Копирование и освобождение

CP сохраняет точные метаданные, зашифрованный DEK и DP-запрос до отправки
`BackupSnapshotData`. Сохранённый запрос означает принятую копию; она
повторяется до успеха или явной отмены.

DP ставит ссылку, ставит в очередь чанки, которых нет в фолловере, и ждёт их
копирования. Чанк, который воркер не смог скопировать, остаётся в очереди и
достаётся следующему воркеру. После всех чанков DP публикует полную карту и
метаданные, сохраняет `Finished`, удаляет записи чанков снапшота и снимает
ссылку. CP выставляет `backup_completed`. Распаковка для CRC, сравнение
содержимого назначения и ремонт объектов в этот PR не входят.

## Сбой и отмена

Состояние CP — точный DP-запрос и ID задачи копии. Повтор после
рестарта находит ту же задачу копии и повторяет только незаконченные шаги.

Явная отмена восстанавливает ID копии, отменяет её и удаляет свою запись
очереди, не дожидаясь копии. `Cancel` DP-копии удаляет записи очереди и
чанков снапшота и последним шагом очищает `backup_task_id`. Новая попытка не
захватит снапшот раньше, поэтому не увидит очистку чужих записей; она ставит
в очередь только чанки, которых ещё нет в фолловере. Воркер, уже читающий
чанк, допишет объект без карты либо запишет его в `follower_chunks` — объект
в этом случае действительно лежит в фолловере. Ошибка очистки повторяется;
она не считается успешной отменой.

## Шифрование

Сохраняется схема main: DEK шифрует данные; KEK на хосте сервиса шифрует DEK.
CP сохраняет зашифрованный DEK и передаёт DP. Каждый объект содержит свой
зашифрованный DEK и идентификатор KEK; AES-GCM получает случайный nonce при записи.

Чанк x, скопированный вместе с A, используется C с собственным конвертом x.
Удаление исходного A или его метаданных не лишает C ключа x: зашифрованный DEK
находится на самом объекте. Карта и метаданные C получают конверт попытки C.
Поддерживается одно настроенное поколение KEK; ротация требует отдельной работы.

## Отдельный PR: наполнение очереди по folder

Второй PR добавляет только автоматическую постановку в ту же очередь.
`snapshots backup-folder --folder-id <id>` сохраняет выбор каталога и отвечает
`OK`. В таблице `backup_folders` находятся `folder_id`, поколение включения и
`enabled`; владельцев копий там нет.

`snapshots.BackupFolder` читает готовые источники без отметки завершения по
индексу каталога и курсору ID. Для каждого вызывает транзакционную постановку
в общую очередь. Состояние производителя — курсор и номер прохода; собственных
удержаний и задач копирования у него нет. Лок и копию каждого снапшота
выполняет тот же путь одного snapshot_id из первого PR.

После конца прохода курсор сбрасывается. Поэтому источник, ставший готовым
позади курсора, будет найден в следующем проходе. Новый номер прохода позволяет
повторно поставить ранее отменённую попытку с новым ключом. Повтор после сбоя
внутри прохода сохраняет ключ и не дублирует уже стоящую запись.

Новые снапшоты выбранного каталога ставятся в очередь той же транзакцией,
которая переводит их в `ready`. Порядок записей не важен: общие чанки
переносит первая копия, которая до них дошла.

`--disable` прекращает автоматическую постановку. Уже поставленные запросы
продолжают исполняться; ручная постановка одного ID остаётся доступной.
Проверка поколения и вставка в очередь выполняются одной транзакцией, поэтому
старый производитель не может ставить записи после отключения или в новом
поколении включения. Пока запись только стоит в очереди и копия не началась,
обычное удаление источника разрешено.

## Первое включение и границы

Сначала применяем CP/DP-схему (`backup_task_id` и `follower_chunks` в
DP, `backup_id` очереди и `backup_completed` в CP) и обновляем все исполнители, затем разрешаем ручные
запросы. Старых исполнителей удаления, не проверяющих ссылки, к этому моменту
быть не должно. Включение конфигурации само не наполняет очередь. Для ручного
пути предварительный обход folder не нужен. Второй PR включает автоматическую
постановку отдельно командой выбора folder.

GC фолловера и аудит объектов остаются отдельно. `follower_chunks` считается
верным, пока объекты фолловера не удаляются; GC должен будет удалять чанк из
таблицы раньше объекта и учитывать ссылки всех опубликованных карт. Отмена может оставить
объекты без опубликованной карты; их очистка требует отдельного протокола.
Живое старое исполнение задачи после потери lease на другом хосте не
ограждается: это ограничение фреймворка задач, а не протокола бекапа.

Добавлены сценарии DP-захвата против Delete, пропуска чанков, уже
записанных создателем, однократного переноса общего чанка удалённого
создателя, принятой копии удаляемого снапшота, восстановления после
сохранённого состояния, отмены и повторной постановки после очистки.
Проверены форматирование, импорты, регистрация файлов и дифф. Сборка и
исполнение тестов — только на cloud после публикации коммитов.
