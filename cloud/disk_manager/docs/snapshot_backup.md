# Бекап снапшотов Disk Manager: защита графа перед копированием

Бекапы в проде ещё не включались. Защита и проверка отдельной копии вводятся
базовым PR; очередь, подготовка графа и admin CLI — следующим PR. Документ
публикуется отдельно от кода.

## Правило удаления

Различаем два удержания в CP:

- `backup_plan_id` — источник включён в подготавливаемый граф. Копирование ещё может не начаться.
- `backup_task_id` — копия принята и должна закончиться даже при поступлении Delete.

Delete может отметить защищённый снапшот как `deleting`, но физическое удаление
ждёт освобождения обоих удержаний. До захвата защиты удаляющийся источник в
граф не принимается. Удаляемый лист плана, копирование которого ещё не началось,
исключаем и освобождаем, если он больше не нужен живым узлам или начатой копии.
Удаляемых предков удерживаем, пока они нужны оставшимся потомкам. После
проверенной копии предка его исходные данные можно отпустить: потомки сохраняют
собственные ссылки на необходимые чанки.

Принятая копия повторяется без лимита до успеха или явной отмены. Обычный Delete
её не отменяет. Удаление снимает только ссылки самого снапшота; общие чанки
удаляются обычным механизмом DP после исчезновения последней ссылки.

## Подготовка графа

Пусть C использует чанки B и A. Сначала защищаем C, затем читаем его полную
карту и определяем создателей ненулевых chunk ID. Для каждого доступного
создателя своего выбранного каталога захватываем защиту и читаем зависимости.
Повторяем, пока не собран весь доступный граф. Только после сохранения графа
и топологического порядка начинаем копировать A, затем B, затем C.

Граф и намерение удержать каждый узел хранятся в состоянии
`snapshots.BackupSnapshot` до обращения к storage. Каждое удержание захватывается
CP-транзакцией на строке снапшота. Пока обход открывает родителей, защищённый
потомок уже сохраняет все ссылки на нужные унаследованные чанки. Все строки не
блокируются одной большой транзакцией; безопасность каждого шага обеспечивается
удержанием потомка и транзакционным захватом следующего источника.

`dataplane.GetSnapshotBackupDependencies` временно удерживает карту во время
чтения, сохраняет список создателей и освобождает DP-удержание. CP-удержание
плана остаётся до исключения узла либо завершения его копирования и задерживает
отправку DP-удаления. Зависимости определяются по карте, а не только по
`BaseSnapshotID`.

Если A уже удалён или Delete выиграл до захвата его защиты, A остаётся в графе
как исключённый узел. Его полный снапшот не восстанавливаем. Нужный C чанк x
сохраняется ссылкой C и копируется через C. Если A уже имеет подтверждённый
бекап, отмечаем его завершённым и используем его объекты без повторного чтения.
Полная карта C сохраняет все ссылки независимо от наличия исходного A.

## Обход выбранного каталога

CP-таблица `backup_folders` хранит выбор `folder_id`, поколение включения,
координатора, владельца текущего плана (`active_plan`) и текущей копии
(`active_owner`). Один координатор каталога ведёт один граф; графы одного
каталога не перекрываются. Предки других каталогов и образы не включаются
неявно: нужные чанки копируются через защищённый выбранный источник.

`snapshots.BackupFolder`:

1. Выбирает `ready` снапшот без `backup_completed` по индексу каталога и курсору ID.
2. Сохраняет корневой ID, уникального владельца и точный ключ дочерней задачи до отправки.
3. Запускает `snapshots.BackupSnapshot`, которая подготавливает и удерживает весь граф этого корня, сохраняет порядок и копирует узлы последовательно.
4. Двигает курсор после завершения или исключения корня и освобождения всего плана.
5. После конца прохода сбрасывает курсор, подхватывая снапшоты, ставшие готовыми позади него. Пустой каталог ждёт следующего исполнения задачи.

Граф готовится для выбранного корня и его зависимостей; всё содержимое каталога
одновременно не удерживается. Старые и новые снапшоты проходят один путь.
Новые `ready` выбранного каталога добавляются в очередь атомарно с переходом
статуса. Ранняя встреча C при обходе не нарушает порядок A → C: её граф раскрывает
A и удерживает источники до копирования. `creating` ждёт готовности.

Admin:

- `snapshots backup-folder --folder-id <id>` сохраняет включение и отвечает `OK`, не дожидаясь копирования.
- Та же команда с `--disable` прекращает новые захваты и копии. Принятая копия заканчивается, оставшиеся удержания плана освобождаются. Повторное включение ждёт освобождения прежнего координатора.
- `snapshots backup --id <id>` ставит готовый снапшот выбранного каталога в очередь. Повторная постановка или уже записанный успех дают `OK`.
- `snapshots get --id <id>` показывает `backup_completed`, `backup_plan_id`, `backup_task_id`: проверенный успех, удержание в плане и принятую копию соответственно.

## Удаляемые листья

Перед каждым шагом копирования, включая повтор исполнения с работающим DP
ребёнком, перечитываем CP-метаданные незавершённых узлов. Готовые узлы и уже
принятые копии служат корнями оставшейся работы. По сохранённым связям находим
всё, что им нужно. Удаляемые узлы вне этого множества исключаем из плана,
сохраняем решение, затем освобождаем их удержания.

Для A → B → C:

- Delete C до начала его копирования освобождает C; живые A/B остаются самостоятельными кандидатами на бекап.
- Удаляемый A при живом C остаётся удержанным и копируется первым.
- Если весь оставшийся граф удаляется и ни одна копия не принята, освобождаем весь граф без копирования.
- Если A уже копируется, Delete A не прерывает копию; ненужный C можно отпустить, пока A заканчивается.

Приём копии повторно проверяет статус транзакционно. Удаляемый лист не
принимается даже при Delete между проверкой графа и приёмом. Уже удержанный
удаляемый предок может быть принят, если он нужен оставшемуся потомку. Гонка с
удалением потомка может привести к лишней принятой копии предка, но не к потере
данных; принятую работу заканчиваем.

## Защита источника при копировании

CP приём записывает `backup_task_id` и слот текущей копии каталога. CP сохраняет
точные метаданные, зашифрованный DEK и DP-запрос до отправки ребёнка. Повтор
того же владельца продолжает принятую работу после Delete или отключения.

DP устанавливает своё удержание транзакционно против `DeletingSnapshot`.
Прямая `DeleteSnapshotData` также проверяет DP-удержание. Карта и все её
зарегистрированные ссылки остаются неизменными во время копирования.

## Полная копия и отметка успеха

CP сохраняет список успешно завершённых зависимостей вместе с точным
DP-запросом. DP под удержанием источника ставит в очередь собственные чанки и
чанки без подтверждённого бекапа создателя. Чанки завершённого предка пропускает.
Создатели, удалявшиеся до захвата защиты, недоступные источники и образы
не принимаются в новые копии неявно: нужные чанки копируются через потомка. Выбор folder ограничивает новые
копии; другие каталоги автоматически не включаются.

Очередь принимает записи только текущего владельца; повторные chunk ID не
увеличивают ожидаемое число независимых объектов. Воркеры читают исходные чанки
с проверкой CRC после распаковки. Существующий объект назначения читается,
расшифровывается и сравнивается с источником и метаданными. При несовпадении
записывается исправный объект.

После окончания чанков DP собирает итоговую полную карту из удерживаемого
источника. Проверяет реальные объекты своих чанков и чанков без подтверждённого
предка; отсутствующие/неверные возвращает в очередь. Объекты успешно завершённых
зависимостей использует без повторного чтения источника и назначения. Ошибка
чтения не снимает удержание. Промежуточного объекта карты в S3 нет.

После проверки публикуются карта и CP-метаданные во фолловере. DP сохраняет
завершение до освобождения удержания, дожидается своих учтённых воркеров и
очищает прогресс. CP после успешного завершения дочерней задачи атомарно
выставляет `backup_completed` и снимает свою резервацию. Тогда уже запрошенное
удаление может продолжиться.

Отметка относится к одному неизменному назначению фолловера и текущему формату.
Смена назначения требует отдельной миграции. Она не заменяет последующий аудит
сохранности опубликованной копии.

## Перезапуск и отмена

В состоянии задачи каталога находятся только курсор, номер попытки, текущий
snapshot ID, owner ID и child task ID. Если отправка задачи удалась, а её ID не
сохранился, повтор использует тот же сохранённый ключ и восстанавливает ту же
задачу. Курсор двигается после долговечного результата ребёнка.

CP-задача сохраняет узлы, связи, индекс раскрытия графа, читателя и его исходный
snapshot ID, готовность графа, топологический порядок и индекс копирования.
Для текущей копии сохраняются точный DP-запрос и ID ребёнка; завершение узла
сохраняется до освобождения источника. Повтор продолжает тот же граф, а не
набирает новый поверх оставшихся удержаний.

Намерение удержать узел сохраняется до захвата. Поэтому отмена находит и
освобождает удержание даже после сбоя между успешным захватом и следующим
сохранением. Потерянный ID читателя/копии восстанавливается по сохранённому
намерению и тому же ключу отправки. Отмена ждёт их завершения и DP-очистки,
затем освобождает удержания всех узлов. Слот плана освобождается только после
исчезновения всех его удержаний; новый координатор не может обойти этот барьер.

Завершённая DP-задача повторяет очистку без нового копирования и без записи
данных после освобождения источника.

Обычное отключение каталога (`enabled=false`) прекращает новый приём и даёт
уже принятой копии закончиться. Запись каталога остаётся до освобождения
координатора; повторное включение с новым поколением ждёт окончания старой
работы. Поздний запрос прежнего координатора не принимается новым поколением.

Явная отмена задачи каталога отключает его, восстанавливает неизвестный ID
ребёнка, отменяет его и ждёт окончания очистки. Отмена CP-копии ждёт своего DP
ребёнка, очищает очередь/учёт воркеров через `dataplane.ReleaseSnapshotBackup`,
освобождает DP-удержание, затем CP-удержания всего графа и слот плана. Другого владельца она не трогает.

## Шифрование

Сохраняется схема main: DEK — ключ данных попытки; KEK хранится на хосте сервиса
и шифрует DEK. CP сохраняет зашифрованный DEK и передаёт его DP. AES-GCM использует
отдельный случайный nonce при каждой записи. Каждый объект содержит свой
зашифрованный DEK и идентификатор KEK в метаданных.

Если исправный чанк x уже скопирован вместе с A, бекап B повторно использует
объект с его собственным конвертом. Удаление метаданных A не лишает B возможности
расшифровать x: нужный зашифрованный DEK лежит на самом объекте x. Карта B и её
метаданные получают конверт попытки B. Сейчас поддерживается одно настроенное
поколение KEK; ротация с чтением старых ключей требует отдельной работы.

## Включение и границы этой версии

Бекапы в проде ещё не включались. Это первое включение: переход с работающего
бекапа, перенос его прогресса и сверка прежних копий не нужны.

1. Пока список выбранных каталогов пуст, применяем CP/DP-схему и индекс.
2. Обновляем все CP/DP исполнители. До включения не должно остаться исполнений
   удаления на старом коде, который не проверяет удержания.
3. Включаем выбранные `folder_id`. Координатор начинает обычный обход: существующие
   и новые `ready` снапшоты проходят один путь и копируются по одному.

Источники, уже удалявшиеся до захвата защиты, не принимаются в новый план.
Удаляемые узлы уже удержанного плана обрабатываются по правилам листьев и
предков. Принятую копию заканчиваем перед физическим удалением. Перед
копированием требуется раскрыть граф корня; предварительного удержания всего
каталога не требуется.

Механизм защищает источники снапшотов и проверяет полную копию. Бекап образов
остаётся на прежнем CP-пути. GC фолловера, его общие ссылки/читатели и ограждение
поздних S3 PUT остаются следующей работой. Учёт воркеров по логическому task ID
не доказывает прекращения старого исполнения при потере lease и не является
достаточной защитой для будущего GC. Перед добавлением удаления копий во
фолловере нужны ссылки/удержания завершённых зависимостей: порядок A → C
не должен позволить удалить чанки A между его завершением и публикацией C.
Отмена может оставить чанки без опубликованной карты; их очистка требует
отдельного протокола.

## Проверки

Добавлены сценарии принятия против Delete, ожидания CP перед DP, освобождения
общего чанка после последней ссылки, копирования потомка с удалёнными предками,
полноты карты/объектов, удержания графа до копирования, порядка A → C,
удаляемых листьев и предков, восстановления удержания после сбоя сохранения,
пропуска чтения завершённого предка,
шифрования, восстановления неизвестного child ID,
продолжения текущей копии при отключении и запрета одновременного повторного
включения. Локально проверяются форматирование, регистрация файлов и дифф.
Сборка и тесты выполняются только на cloud после публикации снимка ветки.
