# Бекап снапшотов Disk Manager: удерживаем только текущую копию

Протокол защиты источника и последовательного бекапа выбранных каталогов.
Бекапы в проде ещё не включались; ниже описаны реализация и порядок первого
включения. Защита источника и проверка полной копии вводятся отдельно от
обхода каталогов, заполнения очереди и admin CLI. Этот документ — отдельное
изменение без кода.

## Правило удаления

- До принятия бекапа снапшот можно удалить. Он исключается из очереди; новую копию не начинаем.
- После принятия бекапа его физическое удаление ждёт окончания полной копии и освобождения удержания.
- При удалении снапшота снимаются только его ссылки на чанки. Другие потребители сохраняют свои ссылки; данные удаляются после исчезновения последней ссылки.
- Ошибка принятой копии не снимает удержание автоматически. Работа повторяется без лимита до исправления или явной отмены.

Принятие — конкретная CP-транзакция, которая проверяет готовность ресурса и
записывает `backup_task_id`. Запись в очереди, выбор ID при обходе и сохранение
намерения отправить дочернюю задачу ещё не означают принятия.

## Почему можно удалить предка

Пусть A создал чанк x, а готовый B унаследовал x. При создании B DP сохранил
запись в собственной карте B и зарегистрировал ссылку B на x. Удаление A
снимает ссылку A; ссылка B остаётся, поэтому x сохраняется.

Если A существует и ещё не скопирован, сначала заканчиваем бекап A, затем
принимаем B. Подтверждённые чанки A повторно не копируем и не перечитываем.
Если A уже удалён, удерживаем B и копируем нужный ему x из источника B.
Полная карта B сохраняет все ссылки, независимо от наличия A в продовой базе.
После освобождения удержания B его удаление снимает ссылку B. Если потребителей
больше нет, обычный механизм DP удалит x. Образы и другие ветки также учитываются
существующими ссылками DP. Для создаваемого потомка действуют существующие локи
создания, пока его собственные ссылки не зарегистрированы.

Связи определяем по создателям ненулевых chunk ID в карте DP, а не только по
`BaseSnapshotID`. Отдельная задача `dataplane.GetSnapshotBackupDependencies`
на короткое время удерживает карту для чтения, сохраняет список создателей и
освобождает источник. Это ещё не принятие копии в CP. Предварительных удержаний
всего каталога и отдельной таблицы общего плана нет.

## Обход выбранного каталога

CP хранит `folder_id`, а DP получает конкретные `snapshot_id`. В CP-таблице
`backup_folders` находятся список выбранных каталогов и состояние координатора:
`generation`, `enabled`, `coordinator_task_id`, `active_owner`.

Одна длительная задача `snapshots.BackupFolder` обрабатывает один каталог:

1. Выбирает следующий `ready` снапшот без `backup_completed` по индексу `folder_id_index` и курсору ID.
2. Сохраняет ID, уникального владельца и точный ключ дочерней задачи в собственном состоянии до отправки.
3. Запускает `snapshots.BackupSnapshot`. Перед принятием источника задача читает его зависимости через DP и рекурсивно дожидается бекапов доступных предков своего каталога. `WaitTask` обеспечивает топологический порядок: A заканчивается перед C. Одновременно копируется один источник; ожидающие потомки не удерживаются на всё время ожидания.
4. После проверенной полной копии либо исключения до принятия сохраняет продвижение курсора и берёт следующий ID.
5. Дойдя до конца, сбрасывает курсор. Это подхватывает снапшоты, ставшие готовыми позади него. Когда подходящих ресурсов нет, задача прерывает исполнение и ждёт следующего запуска.

Старые и новые снапшоты проходят один и тот же путь. Новые `ready` выбранного
каталога атомарно добавляются в CP-очередь при смене статуса и становятся
кандидатами для следующих шагов обхода. Общего этапа подготовки старого набора
и обязательного ожидания его окончания больше нет. Порядок ID — порядок обхода,
а реальный порядок копирования определяется зависимостями задач.

`creating` ждёт перехода в `ready`. `deleting`/`deleted`, обнаруженные до принятия,
не копируются. Бекапы ещё не включались, поэтому при первом обходе существующие
`ready` снапшоты копируются впервые. После включения незавершённая попытка может
оставить объекты в фолловере: при повторе их наличие не заменяет проверку полноты.

Управление через admin:

- `snapshots backup-folder --folder-id <id>` — включает обход существующих и новых готовых снапшотов. Возвращает `OK` после сохранения выбора каталога, не ждёт копирования.
- `snapshots backup-folder --folder-id <id> --disable` — прекращает приём новых копий; принятая копия заканчивается. Повторное включение ждёт освобождения прежнего координатора.
- `snapshots backup --id <id>` — ставит готовый снапшот выбранного каталога в очередь. Повторная постановка или уже записанный успех дают `OK`; порядок обхода остаётся общим для каталога.
- `snapshots get --id <id>` — показывает `backup_completed` и `backup_task_id`. `true` подтверждает полную проверенную копию; непустой владелец означает принятую попытку. `false` без владельца не различает ещё не выбранный ресурс и отменённую попытку.

## Принятие и защита источника

CP `ReserveSnapshotBackup` и CP Delete читают/изменяют одну строку снапшота в RW
транзакциях. Для нового бекапа нужны `ready`, отсутствие отметки полного успеха,
выбранный каталог и совпадающий координатор. Та же транзакция записывает
`backup_task_id` и `backup_folders.active_owner`; в одном каталоге одна активная
копия. Повтор владельца уже принятой копии разрешён после CP `deleting` или
отключения каталога.

Если Delete выиграл транзакционную гонку, бекап получает отказ до принятия и
успешно завершается с `Completed=false`. Если бекап выиграл, Delete записывает
CP `deleting`, но ждёт `backup_task_id` перед отправкой физического DP-удаления.
Этот барьер закрывает окно до установки DP-удержания.

CP сохраняет исходные метаданные, зашифрованный DEK и точный DP-запрос до
отправки дочерней задачи. DP проверяет `ready` и устанавливает своё удержание
того же владельца транзакционно против `DeletingSnapshot`. Прямая
`DeleteSnapshotData` также проходит эту проверку перед чтением карты.

Удержание сохраняет карту текущего источника и его зарегистрированные ссылки
на все унаследованные чанки. Дополнительных рекурсивных локов на предках нет.

## Полная копия и отметка успеха

CP сохраняет список успешно завершённых зависимостей вместе с точным
DP-запросом. DP под удержанием источника ставит в очередь собственные чанки и
чанки без подтверждённого бекапа создателя. Чанки завершённого предка пропускает.
Недоступные/удаляемые создатели и образы не принимаются в новые задачи неявно:
нужные чанки копируются из текущего потомка. Выбор folder ограничивает новые
копии; другие каталоги автоматически не включаются.

Очередь принимает записи только текущего владельца; повторные chunk ID не
увеличивают ожидаемое число независимых объектов. Воркеры читают исходные чанки
с проверкой CRC после распаковки. Существующий объект назначения читается,
расшифровывается и сравнивается с источником и метаданными. При несовпадении
записывается исправный объект.

После окончания чанков DP собирает итоговую полную карту из удерживаемого
источника. Проверяет реальные объекты своих чанков и чанков без подтверждённого
предка; отсутствующие/неверные возвращает в очередь. Объекты успешно завершённых
зависимостей использует без повторного чтения источника и назначения. Ошибка
чтения не снимает удержание. Промежуточного объекта карты в S3 нет.

После проверки публикуются карта и CP-метаданные во фолловере. DP сохраняет
завершение до освобождения удержания, дожидается своих учтённых воркеров и
очищает прогресс. CP после успешного завершения дочерней задачи атомарно
выставляет `backup_completed` и снимает свою резервацию. Тогда уже запрошенное
удаление может продолжиться.

Отметка относится к одному неизменному назначению фолловера и текущему формату.
Смена назначения требует отдельной миграции. Она не заменяет последующий аудит
сохранности опубликованной копии.

## Перезапуск и отмена

В состоянии задачи каталога находятся только курсор, номер попытки, текущий
snapshot ID, owner ID и child task ID. Если отправка задачи удалась, а её ID не
сохранился, повтор использует тот же сохранённый ключ и восстанавливает ту же
задачу. Курсор двигается после долговечного результата ребёнка.

CP-задача сохраняет ID читателя зависимостей, текущей задачи предка, индекс
обхода и успешно завершённые ID. Потерянные после отправки ID восстанавливаются
тем же ключом. Отмена сначала отменяет эти дочерние задачи и ждёт их очистки.
Затем CP-задача освобождает собственный источник; раннего освобождения
координатора при работающем предке нет.

Дочерняя CP-задача аналогично сохраняет точный DP-запрос перед отправкой.
Завершённая DP-задача после сбоя повторяет освобождение, не начинает новый
бекап и не переписывает данные после удаления источника.

Обычное отключение каталога (`enabled=false`) прекращает новый приём и даёт
уже принятой копии закончиться. Запись каталога остаётся до освобождения
координатора; повторное включение с новым поколением ждёт окончания старой
работы. Поздний запрос прежнего координатора не принимается новым поколением.

Явная отмена задачи каталога отключает его, восстанавливает неизвестный ID
ребёнка, отменяет его и ждёт окончания очистки. Отмена CP-копии ждёт своего DP
ребёнка, очищает очередь/учёт воркеров через `dataplane.ReleaseSnapshotBackup`,
освобождает DP-удержание и затем CP-резервацию. Другого владельца она не трогает.

## Шифрование

Сохраняется схема main: DEK — ключ данных попытки; KEK хранится на хосте сервиса
и шифрует DEK. CP сохраняет зашифрованный DEK и передаёт его DP. AES-GCM использует
отдельный случайный nonce при каждой записи. Каждый объект содержит свой
зашифрованный DEK и идентификатор KEK в метаданных.

Если исправный чанк x уже скопирован вместе с A, бекап B повторно использует
объект с его собственным конвертом. Удаление метаданных A не лишает B возможности
расшифровать x: нужный зашифрованный DEK лежит на самом объекте x. Карта B и её
метаданные получают конверт попытки B. Сейчас поддерживается одно настроенное
поколение KEK; ротация с чтением старых ключей требует отдельной работы.

## Включение и границы этой версии

Бекапы в проде ещё не включались. Это первое включение: переход с работающего
бекапа, перенос его прогресса и сверка прежних копий не нужны.

1. Пока список выбранных каталогов пуст, применяем CP/DP-схему и индекс.
2. Обновляем все CP/DP исполнители. До включения не должно остаться исполнений
   удаления на старом коде, который не проверяет удержания.
3. Включаем выбранные `folder_id`. Координатор начинает обычный обход: существующие
   и новые `ready` снапшоты проходят один путь и копируются по одному.

Уже удаляемые снапшоты не принимаются в бекап. Если Delete пришёл после принятия,
копию заканчиваем и только затем продолжаем физическое удаление. Предварительного
обхода для блокировки всего каталога не требуется.

Механизм защищает источники снапшотов и проверяет полную копию. Бекап образов
остаётся на прежнем CP-пути. GC фолловера, его общие ссылки/читатели и ограждение
поздних S3 PUT остаются следующей работой. Учёт воркеров по логическому task ID
не доказывает прекращения старого исполнения при потере lease и не является
достаточной защитой для будущего GC. Перед добавлением удаления копий во
фолловере нужны ссылки/удержания завершённых зависимостей: порядок A → C
не должен позволить удалить чанки A между его завершением и публикацией C.
Отмена может оставить чанки без опубликованной карты; их очистка требует
отдельного протокола.

## Проверки

Добавлены сценарии принятия против Delete, ожидания CP перед DP, освобождения
общего чанка после последней ссылки, копирования потомка с удалёнными предками,
полноты карты/объектов, порядка A → C, пропуска чтения завершённого предка,
шифрования, восстановления неизвестного child ID,
продолжения текущей копии при отключении и запрета одновременного повторного
включения. Локально проверяются форматирование, регистрация файлов и дифф.
Сборка и тесты выполняются только на cloud после публикации снимка ветки.
